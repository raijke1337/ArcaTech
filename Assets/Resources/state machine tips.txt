Good — you already have a working intent-driven FSM; integrating other components that can also trigger states is mostly about (A) defining how those components signal intent/events, (B) ensuring the state machine evaluates transitions continuously and with priorities, and (C) providing safe “forced”/interrupt transitions for high‑priority events (stun, death). Below I give a clear, practical design and copy‑pasteable code snippets that show several patterns you can mix:

- global (high priority) transitions evaluated before per‑state transitions,
- transition conditions that read component state (no tight coupling),
- components either enqueue intents (preferred) or call ForceUnitState for immediate interrupts,
- how to wire Interaction/Usables/EntityStats into the FSM,
- a checklist for migration and tests.

Design summary (short)
- Keep the state machine authoritative: components report intent or state; the state machine decides to transition or perform forced interrupts.
- Add global transitions (or an interrupt list) that the state machine checks before the current state’s transitions. Use numeric priority so Stunned/Dead outrank other transitions.
- Implement TransitionCondition SOs that inspect component properties (e.g., `IsStunned`, `IsDead`, `InteractionSucceeded`, `IsDamaged`) rather than making components push states directly.
- For immediate interrupts (Death absolutely must interrupt), allow components to call `ForceUnitState(...)` on the state machine.
- For success/failure events that are the result of a component action (e.g., `InteractionComponent` finishes UseSuccess), either:
  - set a `ctx.PendingCommand`/event and let the FSM evaluate transitions immediately, or
  - call a `RequestEvent(...)` method on the FSM (which sets the event in the context then runs `EvaluateTransitions()`).
- Always evaluate transitions in `Update()` (you already do) and check global transitions first.

1) Add a global/interrupt transition list to `EntityStateMachineComponent`
- Evaluate these before per‑state transitions every frame.

```csharp
// EntityStateMachineComponent.cs (excerpt)
public class EntityStateMachineComponent : MonoBehaviour
{
    // existing fields...
    private List<StateTransition> _globalTransitions = new List<StateTransition>();

    // Public API for systems to register global transitions if desired
    public void RegisterGlobalTransition(StateTransition t)
    {
        if (t == null) return;
        if (!_globalTransitions.Contains(t)) _globalTransitions.Add(t);
    }

    public void UnregisterGlobalTransition(StateTransition t)
    {
        if (t == null) return;
        _globalTransitions.Remove(t);
    }

    void Update()
    {
        if (CurrentState == null) return;
        if (Paused) return;

        CurrentState.Update(_context, Time.deltaTime, animator);

        // Allow chained transitions but protect from infinite loops
        int iter = 0;
        const int maxIter = 8;
        while (iter++ < maxIter)
        {
            if (!EvaluateTransitions()) break;
        }
    }

    // Try to find a transition from globals first, then current state's transitions
    bool EvaluateTransitions()
    {
        // Evaluate global transitions (highest priority)
        var orderedGlobals = _globalTransitions.OrderByDescending(t => t.Priority);
        foreach (var g in orderedGlobals)
        {
            if (g == null || g.NextState == null) continue;
            if (!g.CanTransition(_context)) continue;
            // If this transition requires exit time, check it (pass CurrentState.animator info if needed)
            // Here we assume StateTransition carries ExitNormalizedTime and we can call helper
            if (!HasPassedExitTimeForCurrentState(g.ExitNormalizedTime)) continue;

            // Run onTransition actions (performers). Abort on any failure
            if (!ExecuteTransitionActions(g)) { _context.ClearCommand(); return false; }

            CommitTransition(g);
            return true;
        }

        // Evaluate current state's transitions
        if (CurrentState == null) return false;
        var candidate = CurrentState.ChooseTransition(_context, animator);
        if (candidate == null || candidate.NextState == null) return false;

        if (!ExecuteTransitionActions(candidate)) { _context.ClearCommand(); return false; }

        CommitTransition(candidate);
        return true;
    }

    bool ExecuteTransitionActions(StateTransition tr)
    {
        if (tr.OnTransition == null) return true;
        foreach (var a in tr.OnTransition)
        {
            if (a == null) continue;
            bool ok = a.ProduceResult(gameObject, _context.PendingCommand, /*spawnPoint*/ null);
            if (!ok) return false;
        }
        return true;
    }

    void CommitTransition(StateTransition tr)
    {
        CurrentState.Exit(_context, animator);
        CurrentState = tr.NextState;
        _context.CurrentState = CurrentState;
        CurrentState.Enter(_context, animator);
        _context.ClearCommand();
    }

    bool HasPassedExitTimeForCurrentState(float requiredNormalized)
    {
        // Use the UnitState helper HasPassedExitTime (or a dedicated helper).
        return CurrentState == null || CurrentState.HasPassedExitTime(animator, requiredNormalized);
    }

    // Forceful immediate switch (bypass transition checks / performers)
    public void ForceUnitState(UnitState forcedState, bool immediate = true)
    {
        if (forcedState == null) return;
        CurrentState?.Exit(_context, animator);
        CurrentState = forcedState;
        _context.CurrentState = CurrentState;
        CurrentState.Enter(_context, animator);
        _context.ClearCommand();
    }
}
```

Notes:

3) Components should signal via context or events (two patterns)

Pattern A — Components set state flags and the FSM polls conditions
- Components set booleans (`IsStunned`, `LastUseSucceeded`) or update internal state.
- FSM has `SerializedStateTransitionCondition` SOs that check those booleans each frame. This is simple and decoupled.

Pattern B — Components push event to FSM (for one-shot, immediate handling)
- Components call FSM API directly for urgent events: `stateMachine.RequestExternalEvent(EventType)` or `stateMachine.ForceUnitState(...)`.
- Use this for Death (immediate), or if you need instant responsiveness before next Update.

Example small API on `EntityStateMachineComponent`:

```csharp
// called by components for one-shot events (e.g., interaction success)
public void RequestEvent(string eventName)
{
    // convert eventName to PendingCommand / or set a named flag on ctx
    _context.PendingCommand = MapEventToCommand(eventName);
    // Evaluate immediately for responsiveness
    EvaluateTransitions();
}
```

4) Integrate `UsablesCasterComponent`, `InteractionComponent`, `EntityStatsComponent`

- `UsablesCasterComponent` (executor) remains implementing `IUnitCommandHandler.DoUnitCommand(...)`. It will be invoked by `PerformCommandActionSO` during transition evaluation. It can also set a state on the component (e.g., `LastCastSucceeded`) which conditions can check later.

- `InteractionComponent`:
  - On success, set `LastUseSucceeded = true` (or call `stateMachine.RequestEvent("UseSuccess")`).
  - Create a `SerializedStateTransition` that uses `InteractionSuccessConditionSO` to move to `UseSuccessState`.
  - `UseSuccessState.OnEnterActions` can clear the `LastUseSucceeded` flag or run `ActionResult` to perform logic.

- `EntityStatsComponent`:
  - When stunned is applied, set `IsStunned = true` and optionally call `stateMachine.RequestEvent("Stunned")` or rely on `StunnedConditionSO` to be true next frame.
  - For `Dead`, call `stateMachine.ForceUnitState(deathState, immediate:true)` to guarantee immediate transition ignoring other checks.

5) Priority & interrupt rules
- Use `StateTransition.Priority` (higher executes first). Ensure global transitions have higher priority:
  - `Dead` transitions: priority = 1000
  - `Stunned` transitions: priority = 900
  - Player-initiated transitions (attack, jump): priority = 500
  - Movement transitions: priority = 100
- In `EvaluateTransitions`, sort globals and current state transitions by priority.

6) Preventing race conditions and duplicated execution
- Decide who clears one-shot flags (component or action):
  - If conditions simply read `LastUseSucceeded`, the FSM should clear it once it consumes it (e.g., inside `ExecuteTransitionActions` or after commit).
  - Alternatively, the component itself can clear the flag when FSM requests it (less desirable).
- If `OnTransition` action invokes the component (e.g., `PerformCommandActionSO` calling `UsablesCaster.DoUnitCommand(...)`), let that action return success/fail and clear command only after success.

7) Example sequence for Interaction -> UseSuccess
- `InteractionComponent` tries to use object; on server/logic success:
  - Set `interaction.LastUseSucceeded = true` (or call `stateMachine.RequestEvent("UseSuccess")`).
- FSM Update polls transitions, `InteractionSuccessConditionSO` returns true.
- FSM picks the `InteractionSuccess -> UseSuccessState` transition (global or state transition).
- FSM runs `transition.OnTransition` actions (which may call `UsablesCaster` or trigger VFX).
- If actions succeed, FSM commits the state, runs `UseSuccessState.Enter()`.
- After committing, FSM clears `ctx.PendingCommand` and/or calls `interaction.ClearLastUse()`.

8) Layered state machines (optional advanced)
- For clarity you can split locomotion (idle/move/jump/land) and action (attack/use) into separate sub-machines or layers:
  - Locomotion SM: Idle/Move/Jump/MidAir/Land; controls root motion / movement locks.
  - Action SM: Idle/Attacking/Using; controls upper body via an Animator layer mask.
- This reduces coupling and simplifies per-component integration: `UsablesCaster` only interacts with the Action SM; `MovementController` uses Locomotion SM. Interactions between them are still necessary (e.g., attack may disable movement by setting `AllowsMovement` in the action SM and communicating to the locomotion SM).

Conclusion
- Use global/priority transitions for interrupts like Death & Stun (evaluated each frame before state-specific transitions).
- Prefer condition SOs that read component properties so each component stays responsible for its own state, and the FSM remains the authority for switching states.
- For one-shot events, either push events into the FSM (call `RequestEvent`/`ForceUnitState`) or set component flags that the FSM consumes.
- Keep `OnTransition` actions synchronous and return success/failure so the FSM can commit atomically (your chosen Approach A).
